## Overhead Name Drawing (`CNameBox`)

Names are drawn inside the sprite batch that `CGameStateMain::Render_GameMENU` opens around `g_pViewMSG->Draw()`, so `drawFont`'s `bUseSprite` argument must be **true** there. The `false` overload takes a branch that calls `begin_sprite` itself and asserts no batch is active (`zz_font_d3d.cpp:165`); calling it inside the batch corrupts the sprite state and the damage shows up later as an unrelated `sprite_began()` assert at `zz_font_d3d.cpp:312`. Debug probes using the screen-coordinate overload are therefore not safe here.

**`DrawMyName` drew nothing while its name rect sat below the transform origin, and moving it above fixed it.** It drew the player's name into `{0, 0, 115, 14}` -- over the gauge -- and produced no glyphs at all, despite a reached call site, a non-empty name, white colour, a valid font handle, a correct transform and a measured text extent (14px) that fits the rect. Every one of those was verified by tracing before the cause was found. The non-sprite overload rendered the same string fine, so neither the font nor the string was at fault. `DrawMyName` now matches `DrawMobName`'s targeted branch, which draws into a rect *above* the origin (`{..., -18, ..., 0}`); that is why the player's name sits above the bar rather than inside it.

**Moving the name above the bar means the clan row has to move too.** `GetClanMarkDrawPos` places the clan mark/name at `y - NAMEBOX_HEIGHT/2 - 20`, which assumes the name sits at the gauge's height -- true for other players, false for `DrawMyName` since the fix above. With `SHOWMYNAME=1` a clanned player saw their clan drawn over their own name while everyone else saw it correctly. `DrawMyName` now passes `y - iHeightNameRow` (18, the same value as the name rect), giving clan / name / gauge.

**Everything above a player's head stacks on `CNameBox::GetPlayerNameStackTop`** (2026-10-06): the top of the name row, or of the clan row when there is one, mirroring `DrawAvatarName` / `DrawMyName` (including the shown-name options). The personal shop sign (`CPersonalStoreManager::GetSignTop`) keeps its retail 70 px but is lifted above that stack, and a player's speech bubble (`CChatBox::Draw`) keeps its retail bottom at `y - 68` but is lifted above the sign while a shop is open, else above the stack. All three used to be fixed offsets, so a clanned shop owner had the clan row under the sign, and once the sign was lifted, the bubble on the sign. Change one row's layout in `CNameBox` and the constants there (`kMyNameRowHeight`, `kClanRowOffset`, `kNameRowOffset`) carry the rest.

**Overhead labels hold their pixel (2026-10-06).** `worldToScreen` floors to whole pixels (fractional sprite positions blur text), and the follow camera keeps easing by sub-pixel steps for a second or two after the player stops moving or turning, so the floored anchor flipped between neighbouring pixels and every name, clan row, NPC title, shop sign and bubble shook on the spot while the scene itself drifted smoothly. `CObjCHAR::StabilizeLabelPOS`, called at the end of `CObjCHAR::GetScreenPOS` (which every character, NPCs included, uses; the NPC height lives in `GetOverheadZ`), holds the last returned pixel and moves only when the floored position leaves it by more than one pixel, trailing by one; an anchor unused for 200 ms is taken fresh. Because every overhead piece reads `GetScreenPOS`, they stay in step with each other. If labels ever look one pixel late in fast motion, this is why. The camera's own tail (`zz_camera_follow::interpolate_camera`, and look mode re-marking itself dirty while parked within its 10 cm dead zone) is untouched -- that is the engine-side fix, still open.

**The underlying rule is not understood** -- below-origin rects work elsewhere in the same batch (`DrawMobName`'s untargeted branch and both `DrawAvatarName` branches draw into `{0, 0, ...}`), so rect position alone does not explain `DrawMyName`'s failure; the fix matches a working call site rather than explaining it. If this bites again, diff `DrawMyName`'s old transform/rect setup against those sites.

**A monster's label height is `max(LIST_NPC col 42, measured model height)`** (2026-10-06,
now `CObjCHAR::GetOverheadZ`, 2026-10-07, which the damage digits share -- they used
`Get_CurPOS().z + m_fStature`, ignoring col 42 and the model's altitude, and their quad was depth
tested, so a wide model rising near its full height in front of the origin column buried the
number in its body; `CDigitEffect` now draws with z test and z write off, like the label). Col 42 is an absolute cm override that ignores `NPC_SCALE`, and it used to
replace the measured height outright, so 26 rows drew their name and bar inside the model: Mega Drake
(100 cm on an ~885 cm model), Hebarn 4148 (550 vs ~1340), Wolf King, Evil Fairy 2725 (270 at scale
200), Grandmaster Golem, Deadly Drake, Ikaness Mecha... The other 263 non-zero rows sit *above* the
bind-pose mesh on purpose -- bees, bats, gargoyles and other flyers hover through animation, which
`getModelHeight` cannot see -- and are unchanged. A new import needs no col 42 unless it flies.

## Summon Info Panel

`CSummonInfoPanel` (`interface/csummoninfopanel.cpp/h`, owned by `CUIMediator` as `m_SummonPanel`) is a draggable overlay listing the player's active summons (name, ATK/DEF/LV/RES, HP bar). It is **not** a tgamectrl dialog — it draws directly with `g_DrawImpl.DrawFit` (`ID_BLACK_PANEL` background, `UI00_GUAGE_*` HP bar) + `drawFont`, like the monster-HP namebox feature, so it needs **no XML resource**. Drawn inside the HUD sprite block via `CUIMediator::Draw()`.

- Visible only when `g_pAVATAR->GetCur_SummonCNT() > 0`; one box per summon, stacked vertically. Summon object indices come from `CObjUSER::GetSummonedMobList()` (the same `m_SummonedMobList` the summon counter/CTRL-click control use); each index resolves to a live `CObjMOB` via `g_pObjMGR->Get_ClientCharOBJ`.
- **Summon gauge lifecycle** (`m_SummonedMobList` / `m_iSummonMobCapacity`, keyed by *server* object index): entries are added on the summon-spawn `gsv_MOB_CHAR` packet and removed by `SubSummonedMob()` in **four** receive paths — lethal FlatBuffer `CombatSwing` (`recv_combat_swing`) and `DamageEvent` (`recv_damage_event`) in `cnetwork.cpp`, plus legacy `GSV_DAMAGE` and `GSV_DAMAGE_OF_SKILL` with `DMG_BIT_DEAD` (`recvpacket.cpp`). All four decrement at packet receive, before any defender/visibility early-outs, so the gauge updates even when the summon object doesn't exist client-side; `SubSummonedMob` on an unknown index is a no-op, which also makes duplicate death packets safe. Do not move the decrement to `Dead()`/presentation time — a queued death presentation can be dropped, and the gauge gates re-summoning (`skill.cpp` capacity check), so a leaked entry eventually blocks the summon skill. The server mirrors lethal packets to out-of-range owners (see gameserver `CLAUDE.md`).
- **Stats are the server-scaled values, not the raw NPC table.** A summon's real combat power is scaled at creation by summon-skill level + owner level (server `CObjSUMMON::SetCallerOBJ`, `cobjnpc.cpp`). The client replicates those exact formulas once at summon time in `recvpacket.cpp` (right next to the pre-existing MaxHP scaling) and stores ATK/DEF/RES + the summon level (= owner level at summon) into `SummonMobInfo` via `SetSummonedMobStats`. **If you change the scaling formula on the server, change it here too** — the two are intentionally duplicated. HP/MaxHP are read live from the object.
- **A summon's max HP comes from the packet, for every viewer (2026-09-21).** `gsv_MOB_CHAR`'s tail is `owner idx, [summon skill idx, int max HP]` (server `CObjCHAR::Add_ADJ_STATUS`; the int is `memcpy`'d, the tail is short-aligned). `CObjMOB::Create` seeds every mob with the wild-monster `NPC_HP * NPC_LEVEL`, and the scaled override used to live inside the `pChar->IsA(OBJ_USER)` block with `g_pAVATAR->Get_LEVEL()` — so only the *owner's* client corrected it and any other player targeting the summon read e.g. `2895/141752`. It cannot be rebuilt on an observer: the formula needs the owner's level *at summon time*, and the owner may not be in the observer's object list at all. The local formula survives only as a fallback for a packet without the field (owner block, and an owner-level approximation for observers). Client and server ship together (tail grew 4 bytes); a mixed pair degrades to the old behaviour, it does not crash.
- **Drag** is handled in `CGameStateMain::ProcWndMsgInstant` (the synchronous consume path): `WM_LBUTTONDOWN` over the stack starts a drag and returns 1 so the click never reaches avatar-move / dialog hit-testing; `WM_MOUSEMOVE + MK_LBUTTON` while dragging moves the panel; `WM_LBUTTONUP` ends it. Position is in-memory only (resets each launch, default right side below the minimap) — not persisted to INI.

## Monster Inspector

`CMonsterInspectorPanel` (`interface/cmonsterinspectorpanel.cpp/h`, owned by `CUIMediator` as `m_MonsterInspector`) is the window opened by the **Monster Inspector skill** — a `SKILL_CREATE_WINDOW` (type 2) skill with `SKILL_POWER == SKILL_WINDOW_MONSTER_INSPECTOR` (50, defined in `gamecommon/skill.h`). It shows the targeted monster's name/level, live HP bar, LIST_NPC stats (ATK/ACC/DEF/M-DEF/Dodge/speeds/EXP), its drop list as item icons, and a rotating 3D model.

- **Purely client-side — no packet, no MP, no aggro by construction.** `CCreateWindowActionSkill::SendSkillActionReq` opens the panel instead of sending anything; `CSkillManager::GetSkillTargetType` special-cases window type 50 to `SKILL_TARGET_OBJECT` (all other window skills stay `SKILL_TARGET_NONE`), and the STB row's class filter 4 (`SKILL_TARGET_FILTER_MOB`) restricts targets to monsters. Cast flow: click a monster once to *target* it (first click targets, second attacks), then use the skill.
- **Drop list** replicates the table walk of the server's `CCal::Get_DropITEM` for display: union of the mob table (`NPC_DROP_TYPE`, only when `NPC_DROP_ITEM > 0`) and the zone-number row of `ITEM_DROP.STB` (`g_TblDropITEM`, already loaded by the client); slot values 1–4 are redirect groups expanding to columns `26+5g … 30+5g`; values > 1000 are packed items, legacy `type*1000+no` or wide `type*100000+no`, decoded by `rose/common/drop_item_code.h` (shared with `CCal::Get_DropITEM`). Deduped. Hovering an icon shows the **standard inventory item tooltip**: the panel builds a throwaway `tagITEM`/`CItem`, fills a `CInfo` via `CItem::GetToolTip`, and registers it with `CToolTipMgr::RegistInfo` — the tooltip manager draws at the end of `g_itMGR.Update()`, which runs *after* `g_UIMed.Draw()` in `Render_GameMENU`, so registering during the panel draw shows the tooltip the same frame on top of the UI.
- **HP** is read live from the target object each `Update()` (`Get_CharOBJ(idx, false)` so the bar drops to 0 on death) and freezes at the last snapshot when the object despawns; static data stays (the panel keeps working on a dead/gone monster until closed). The object-slot reuse case is guarded by re-checking `Get_CharNO()` against the stored NPC row.
- **3D preview uses the engine's avatar-selection viewport pipeline — no scene insertion, no render-to-texture.** The panel owns a client-only "puppet" clone of the monster model (`g_MOBandNPC` `CCharMODEL` + `::loadModel` with the idle motion + `CreatePART` per body part) that is **never inserted into the scene**. `PuppetDrawInPane()` runs last in the panel's sprite draw: `::flushSprite()` (pushes the already-issued panel sprites — including the double-darkened pane background — under the model), `::setAvatarViewPort(paneRect)` (pane-scoped viewport, z-clear, own orthographic origin-facing camera), `::RenderSelectedAvatar(hModel)` (engine places the model at `(0,0,-1.4)` internal units and calls `update_animation` + `render` itself), `::setDefaultViewPort()`. Because the pipeline has its own fixed camera, world-camera motion (RMB drag etc.) cannot move the preview — the earlier world-anchored version trailed out of the pane during camera rotation. Framing gotchas: engine-*internal* units are meters while `getModelHeight`/interface positions are cm (`ZZ_SCALE_IN/OUT` = ×0.01/×100); the selection camera only has increment APIs (`updateAvatarSelectionCameraLength/Height/Seta`), so absolute framing goes through the shared mirror in `OverlayPanelUtil` (`PaneCameraSetFrame`/`PaneCameraSpin`, defaults 2.15 / −0.10; shared with the Item Preview panel) and sets `view_length = modelH_m * 1.2 * paneRatio` (min 0.7), `view_height = −1.4 + modelH_m/2`, plus `Seta += 0.01`/frame for the spin. Device mesh/texture resources are shared by name with the live on-screen monster, so they're already uploaded despite the puppet never entering the scene. Destroy: `clearRenderUnit` → `DeletePART` each → `unloadModel` (no `removeFromScene` — never inserted). **Motion LOD:** `zz_model::apply_motion` has distance-based LOD — `skip_frames` frame skipping driven by `camdist_square` (full rate < 40, up to 10 skipped frames > 200 internal meters) and an interpolated-vs-keyframe-stepped branch gated by `camtarget_distance_square` (which was an *uninitialized* member, only ever written by the shadowmap pass for in-scene shadow-casting models; now ctor-initialized to 0). `RenderSelectedAvatar` calls `zz_model::reset_motion_lod()` (zeroes all three) before `update_animation`, so UI-driven renders always animate at full rate with smooth sampling regardless of what distance state the model inherited — without this the pane visibly mirrored in-world animation LOD.
- **Input** is routed in `CGameStateMain::ProcWndMsgInstant` *before* the summon panel: every LButtonDown on the panel is consumed (close button / drag start — clicks must not leak into the world and attack), mousemove is consumed only while dragging but always feeds hover coordinates for the drop-icon tooltip.
- **Background:** `ID_BLACK_PANEL` has a brightening gradient baked into the sprite's top rows — `DrawFit`-stretching it over a tall rect shows a wide light band at the top, and tiling it as thin strips repeats the bright top row as periodic white lines. `DrawPanelBg` therefore bypasses `DrawFit` and draws with a **cropped source rect** (bottom quarter of the sprite, minus 1 px filter-bleed margin) stretched over the whole rect via `::drawSprite` + geometry-scale transform — one draw, perfectly uniform; the preview pane draws a second layer for extra darkness behind the model.
- Dummy skill data: LIST_SKILL.STB row appended by `scripts/add-monster-inspector-skill.py` (idempotent; prints the skill id — currently **7001**). Learn in game with GM **`/add skill 7001`** (the SKILL branch is in `Cheat_add`, gated by `B_Cheater()`; there is no `/set skill` — `Cheat_set` has no SKILL branch and fails silently, as does an out-of-range skill id when the server still has the old STB cached). Servers must be restarted after the STB append (tables cached at startup) and client data rebaked/deployed.

## Chat Item Links

Shift+click an item to link it in chat; other players hover the link for the full item tooltip. Client-only — the server relays chat verbatim and needed no changes.

- **Wire format** (`interface/chatitemlink.h/.cpp`): token `<il:XXXXXXXXXXXX>` — 12 uppercase hex chars = the 6 packed bytes of `tagBaseITEM` (header word LE + body dword LE), 17 chars total, max 3 per message (`CHAT_ITEM_LINK_MAX_PER_MSG`). The item **name is never transmitted**: receivers rebuild name, rarity color (`CItem::GetItemNameColor`), and tooltip locally, so links are bounds-checked (`tagBaseITEM::IsValidITEM` + non-empty `ITEM_NAME` — remember the stale-quest `get_cstr` nullptr crash) and unspoofable. Invalid/malformed tokens render as plain text.
- **Send path**: `CSlot::Process` WM_LBUTTONDOWN intercepts SHIFT+click on icons whose `CIcon::IsItemIcon()` is true (only `CIconItem`) → `CChatDLG::AddItemLinkToInput` appends `[Name (grade)] ` to the edit box and stores a `{display, token}` pair in `m_PendingItemLinks`. `CChatDLG::SendLine` (shared by the classic `SendChatMsg` wrapper and UI2's chat) substitutes display→token (skipped for `/` GM commands), then **hard-rejects any message whose `strlen` would exceed `CHAT_MSG_WIRE_MAX` (129)** — the gameserver treats >129 as `IS_HACKING` (`gs_user.cpp` `Recv_cli_CHAT`), so the client must never send it; on reject the input and pending links are kept so the user can shorten. Edited/deleted `[Name]`s simply don't match and go out as plain text; stale pending entries are purged against the current input text on each add. `CSlotBuyPrivateStore`'s shift bulk-buy intercepts before `CSlot::Process`, so store behavior is unchanged.
- **Display path**: `CChatDLG::AppendMsg2ListBox` → `AppendChatLineParsed` decodes tokens (`ChatItemLink_Decode`) into a display string + `t_list_link` ranges and calls `CTListBox::AppendTextEx`. The listbox extension (`tgamectrl/tlistbox.*`) stores per-line link segments (`t_list_item::m_Links`, opaque 8-byte payload = the 6 item bytes) with **pixel extents precomputed at append time** (`PushLineWithLinks` via `GetFontTextExtent` — never measure per-frame; `CTSplitString`'s header warns against it). `AppendTextEx` word-wraps without ever splitting a link (char-walk via `CharNextExA`, breaks at the last space). `Draw` renders link lines run-by-run (plain runs in the line color, links in their rarity color) and hit-tests the hovered link; **every `t_list_item` creation path must init `m_nLinkCount = 0`** (the struct is stack-built without zeroing).
- **Hover tooltip**: `CChatDLG::Update` feeds the mouse pos to all chat listboxes (`SetHoverMousePos`); the listbox records the hovered link during its own `Draw`; `CChatDLG::Draw` then queries `GetHoveredLink`, rebuilds the item (`ChatItemLink_ItemFromBytes`), and registers the standard tooltip (`CItem::GetToolTip` + `CToolTipMgr::RegistInfo`, RMB held = detail view) — same pattern as the Monster Inspector drop icons.
- **Overhead bubbles** are single-color (`CChatBox`), so `Recv_gsv_CHAT` / `Recv_gsv_PARTY_CHAT` pass `ChatItemLink_Strip(msg)` (tokens → plain `[Name]`) to `g_UIMed.AddChatMsg`; the chat-log string keeps the tokens.
- **Alt+click on a link** opens the Item Preview panel for equipment items (see "Item Preview Panel" below); non-equipment links are not consumed.

## Item Preview Panel (Alt+Click try-on)

`CItemPreviewPanel` (`interface/CItemPreviewPanel.cpp/h`, owned by `CUIMediator` as `m_ItemPreview`) shows the player's own character wearing a selected equipment item in a rotating 3D pane — without equipping it, touching the inventory, or sending any packet. Client-only.

- **Open paths (Alt+left-click, both consume the click only when a preview actually opens):**
  - Any `CSlot` item icon (inventory/equip/bank/stores): branch at the top of `CSlot::Process` WM_LBUTTONDOWN, *before* the shift+click chat-link branch. **Ctrl+click was taken** — `CIconItem::Process` already binds Ctrl+LButtonDown to wishlist registration, hence Alt.
  - A chat item link: `CChatDLG::Process` intercepts WM_LBUTTONDOWN with `VK_MENU` down before `CTDialog::Process` and asks `TryOpenHoveredItemLinkPreview()` (reuses the listbox `GetHoveredLink` hover state recorded during draw; item rebuilt from the 6 wire bytes).
- **Previewable types:** face item / helmet / armor / gauntlet / boots / knapsack / weapon / subweapon (`ItemType2BodyPart`). Jewelry and non-equipment return false and the click falls through to normal behavior. Same defensive name/STB-bounds checks as chat links (blanked STB row → no open).
- **Cumulative:** while the panel is open, each further Alt+click adds/replaces that item's body-part override (`m_bOverride`/`m_OverrideItemNo` per part) and rebuilds the puppet, so hat + chest + weapon can be previewed together; same-slot clicks replace. The name line shows the last-added item plus `[+n]` for the other active overrides. Closing the panel clears all overrides (fresh session on next open). A failed rebuild rolls back the just-added override and restores the previous puppet.
- **Puppet:** reuses `CJustModelAVT` (the character-select model viewer) as a by-value member. Parts array = `g_pAVATAR->GetPartITEM(i)` (base values) with the previewed item overriding its body part; the 10-arg `Init` applies the helmet-hair offset (`HELMET_HAIR_TYPE`) exactly like `CObjAVT::Update`. `SetRace(IsFemale())` before `LoadModelVisible` (skeleton fetch is sex-keyed). **Never inserted into the scene:** `SetVisible(false)` right after load makes `UnloadModelVisible`'s internal `RemoveFromScene` a no-op, and `setCollisionLevel(hModel, 0)` undoes the 4 that `LoadModelNODE` sets so the puppet can't be picked. `setRepeatCount(0)` loops the idle motion (`SetMotion(1)` from `LoadModelVisible`; `g_MotionFILE` is loaded at startup, in-game too). Grade/gem glow effects are not replicated — the preview shows the base model.
- **Rendering:** same pane pipeline as the Monster Inspector — `flushSprite` → `setAvatarViewPort(pane)` → `RenderSelectedAvatar` → `setDefaultViewPort`, framed by model height (cm→m) with the same 1.2×/min-0.7 formula.
- **Shared camera mirror (`interface/OverlayPanelUtil.*`):** the engine's avatar-selection camera only has increment APIs, so absolute framing needs a mirror of the singleton's current length/height. That mirror now lives *once* in `OverlayPanel::PaneCameraSetFrame/PaneCameraSpin` — the Monster Inspector's former file-local statics moved there. **Never add another per-panel static mirror:** with two panels open, each panel's stale mirror would mis-frame the other every frame. `OverlayPanelUtil` also hosts the shared `DrawTextAt`/`DrawPanelBg` (ID_BLACK_PANEL bottom-crop background) helpers both panels use.
- **Input:** routed in `CGameStateMain::ProcWndMsgInstant` *before* the Monster Inspector (the item preview is drawn last in `CUIMediator::Draw`, i.e. topmost). All clicks on the panel are consumed (close X / drag start); mousemove is consumed only while dragging.
- **Discoverability — tooltip hint:** `CItem::GetToolTip` appends a final line to every previewable equipment tooltip: `Alt+Click` in green + ": preview on your character" in gray. The green run uses the `TIP_KEY` (`\x03`) inline markup added to `ctstring.h` alongside the existing `TIP_CAT`/`TIP_END` — `CTString::Draw` colors the run `kToolTipKeyColor`, and `CInfo`'s `StripTipMarkup` strips the byte for width measurement (any new markup byte must be added in **both** places or lines mis-measure). The gating type-switch in `GetToolTip` must stay in sync with `ItemType2BodyPart` in `CItemPreviewPanel.cpp`.

## Damage Meter ("/dps")

Client-only DPS meter fed by the authoritative combat event stream. **Zero combat-display behavior changes** — the whole feature is a read-only observer. (Phases 2/3 added two wire fields, `DamageEvent.skill_id` and `source_attacker_id`, as display metadata; nothing in presentation reads them.)

- **Data core** (`gamedata/CDamageMeter.cpp/h`, singleton): fed by a single tap at the end of `CObjCHAR::PushCombatDamageEvent` — the one chokepoint every damage source funnels through exactly once (FlatBuffer `CombatSwing`/`DamageEvent` + all legacy `GSV_DAMAGE` / `GSV_DAMAGE_OF_SKILL` conversions). The tap copies what it needs and never mutates the event, the queue, or presentation state. Recording at queue time is deliberate: damage whose animation is later discarded/folded (hard-control interrupts, drain-on-death) was still real server damage and must count.
- **Attribution field:** `Rose::Combat::DamageEvent.skill_id` (client struct) mirrors the phase-2 wire field `DamageEvent.skill_id` in `combat.fbs` (0 = normal attack/unknown; **display metadata only — presentation logic on both sides must never branch on it**). Sources, in priority order: exact from the wire (`to_client_damage_event`; server threads the skill through `Give_DAMAGE(..., kind, nSkillIDX)` → `Send_combat_damage_event` → `build_damage_event_packet` — currently `Skill_START` SKILL_TYPE_06 passes `Get_ActiveSKILL()` and the shield counter passes `nShieldSKILL`); exact from legacy `GSV_DAMAGE_OF_SKILL` in `ConvertDamageOfSkillToDamage` (`m_nSkillIDX`); heuristic fallback in `recv_damage_event` only when the wire field is 0 (`ProjectileImpact` events → caster's `m_nToDoSkillIDX`/`m_nActiveSkillIDX`). `CombatSwing` intentionally keeps 0 = normal attack. Kind-based labels fill the gaps: `StatusTick` → "DoT", `Immediate` w/o skill → "Other".
- **Classification at record time** (object slots are recycled — names/party membership can't be resolved later): cart/castle-gear attacker **and defender** fold to the rider — use `IsPET()`, which covers `OBJ_CART` and `OBJ_CGEAR` (castle gear is its own object type; an `== OBJ_CART` check silently dropped all castle-gear damage — first in-game regression found). `CObjCastleGear` derives from `CObjCART`, so the `GetParent()` cast is valid for both. Then: self vs own summon (`GetSummonedMobList` by server index) vs party member (`CParty::IsPartyMember(Get_ServerObjectIndex(...))`) vs other. Stranger-vs-mob spectator samples are dropped; everything hitting the avatar (or its mount) is kept. Party members' damage works out of the box because `send_packet_nearby` broadcasts combat events to the 9 surrounding sectors — no extra packets.
- **Dedup guards:** event-key ring `(event_id, attacker, defender)` — synthetic legacy ids live in separate counters and can collide with server ids, hence the composite key — plus a per-defender lethal window (2 s): legacy + FlatBuffer paths can each announce the same death but a defender dies once.
- **Segments:** a fight ends after 6 s without samples (`kIdleGapMs`); the panel keeps showing the last fight while idle. Aggregation is rebuilt on demand (`BuildSnapshot`, capped sample ring) — the view layer holds no state of its own.
- **UI** (`interface/CDamageMeterPanel.cpp/h`, owned by `CUIMediator` as `m_DamageMeterPanel`): direct-draw overlay in the `CSummonInfoPanel`/`OverlayPanelUtil` style (no XML). Views: Damage Done (self + party ranking, self+pets folded into one row), My Skills, Damage Taken; header buttons `[>]` cycle / `[R]` reset / `[X]` close; footer shows the biggest hit. Toggled by the **local** `/dps` chat command (`CChatDLG::SendLine` (shared by the classic `SendChatMsg` wrapper and UI2's chat) intercepts before any send; `/dps reset` clears data). Input routed in `CGameStateMain::ProcWndMsgInstant` between the Monster Inspector and the summon panel, matching draw order. Layout/style constants are grouped in an anonymous namespace at the top of the panel cpp for easy modding.
- **Credit vs. attacker (`source_attacker_id`, phase 3):** the wire's `source_attacker_id` (server index → client index in `to_client_damage_event`) is who the meter *credits* when it differs from `attacker_id`: DoT casters (status ticks keep the victim in `attacker_id` for presentation; poison ticks pass the stored speller + skill) and summon owners (server auto-resolves in `Send_combat_swing`/`Send_combat_damage_event`). In the meter: source ≠ attacker on a non-StatusTick event ⇒ pet sample (own pets → self row + "Pets" skill label; party pets → fold into the party member's row); on a StatusTick it's caster attribution, not a pet. Incoming DoTs show the caster's name; "DoT / Status" remains only for unattributed self-ticks. The own-summon-list check stays as fallback for events without a wire source.
- **Alternative RmlUi view:** with `[VIDEO] RMLUI=1` the `/dps` command opens a CSS-authored meter instead (see "RmlUi UI Layer" in `src/client/rmlui/CLAUDE.md`). It is a second consumer of `BuildSnapshot()` — `CDamageMeter` itself is unchanged, and the legacy panel remains the default.
- **Known limits:** party summons' *legacy-path skill* damage (GSV_DAMAGE_OF_SKILL from a summon) still isn't owner-credited — only FlatBuffer swing/event paths carry `source_attacker_id`; party members are only metered while their fights are within your ~1-sector broadcast range (by design — the meter shows the fight around you); no healing meter (heals arrive as bare stat sync). Possible later: combat-log file export for external tools.
